- 気づき・疑問：
  - 同じ 1 行の変更でも、変化の現れ方は条件によって違った。実験B では、3 回とも検索が `LoRA QLoRA` の 1 回にまとまった。実験C では、検索の回数と引数は変わらず、回答末尾が回の表示から確認問題に変わった。実験A では、検索を省略するようになるという変化は見られなかった。
  - 実験A：検索の指示を消しても、検索はやめなかった（補足の質問を含め 4 回とも検索した）。`search_glossary` の docstring にも「…について答える前に使うこと」と書かれていて、同じ指示が 2 か所にあったため、片方を消しても、もう片方が効いていたと考えられる。1 回目だけ `LoRA` のみを検索したが、`LoRA` の検索結果には部分一致で QLoRA の定義も含まれるため、回答に必要な情報はそろっていた。
  - 実験B：例が `"LoRA"`（1 語）のままでも、3 回とも「まとめて」に従って `LoRA QLoRA` で 1 回だけ検索した。ベースラインでも 2 回検索して requests が 2 なので、2 つの検索は 1 回の応答でまとめて出されていた（trace でも `[tool call]` が 2 行続く）。そのため、LLM の呼び出し回数（requests = 2）は変わらず、ツールの呼び出し回数が減った。input_tokens は 1196 から 885 に減った。ツールを直接呼んで確かめると、ベースラインの 2 回の検索では重複を含めて 5 件の定義が返る（`LoRA` で LoRA・ランク（LoRAのr）・QLoRA、`QLoRA` で QLoRA・LoRA）のに対し、`LoRA QLoRA` では LoRA と QLoRA の 2 件だけだった。モデルに渡る検索結果が小さくなったことが、input_tokens の減少に関係していると考えられる（リクエストごとの内訳は確認していない）。
  - ただし、`LoRA QLoRA` で 2 つとも見つかるのは、`search_glossary` が名前の部分一致でも探す実装だからである。入力全体を一つの用語として扱い、用語名と完全一致させる実装なら、`LoRA QLoRA` では見つからない。説明文に書く使い方は、ツールの実装と合っている必要がある。
  - 指示文の長さと入力トークン数：検索の回数と引数が同じだった実験A の 2・3 回目では、input_tokens が 48 減り（1196 → 1148）、補足の質問でも同じく 48 減った（783 → 735）。実験C では 8 減った（1196 → 1188）。指示文の短縮が、複数回の LLM 呼び出しを通じて入力トークン数に反映された可能性がある。ただし、各リクエストの入力内容やトークン数の内訳までは確認していない。
  - 実験C：確認問題は 3 回とも付き、回を示す行はなくなった。今回の比較では、回答末尾に回を示すかどうかが、この指示の変更に対応して変わった。確認問題は用語集の定義（低ランク行列、量子化）をもとにしていて、答えは書かれていなかった。選択肢を示さずに選択を求める出題があり、出題形式の確認も必要だと感じた。演習の `make_quiz` のように、用語集をもとに一定の形式で問題と答えを作る処理をツール側に持たせることは、出題を安定させる方法の一つだと考えた。ただし、今回はその効果を比較していない。
  - 疑問：実験A で docstring の「答える前に使うこと」も消すと、検索しなくなるのか（今回は、docstring の指示も削除した条件は試していない）。また、`INSTRUCTIONS` と docstring の内容が食い違うとき、モデルはどちらを優先するのか。
  - 限界：各条件 3 回（補足の質問は 1 回）だけの比較である。実験A の 1 回目だけ `LoRA` のみを検索したことや、回答の言い回し・回の表示の書き方の違いが、変更の影響か実行ごとのばらつきかは区別できない。
